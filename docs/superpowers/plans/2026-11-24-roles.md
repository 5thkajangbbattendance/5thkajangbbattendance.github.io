# Roles and Permissions Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Discord-style roles that stack, with See or Change per area, enforced by Firestore rules, built on the `roles` branch and previewed in demo mode. The live site isn't touched.

**Architecture:** Each role is a doc in `roles/`. When the Owner saves a role or an assignment, the browser computes each affected login's combined `access` `{read,write,see,mark}` and writes it to `staff/{uid}` in the same batch. Rules read only `staff/{uid}.access`, falling back to a duty table. The app reads the same object through `can(a)`, `canEdit(a)`, `sees(g)` and `marks(g)`. Pages without Change are locked by one generic read-only pass.

**Tech Stack:** Single-file app (`app.html`, ES5, built by `node build.js`), Firestore rules plus the emulator, the inventory React app (Vite and Vitest), Playwright.

**Spec:** `docs/superpowers/specs/2026-11-24-custom-access-design.md`

## Global Constraints

- Area ids: `run, reports, roster, changes, cs, web, notices, enquiries, orders, unisetup, drive, inv, invImport, invSheet, staff`.
- Group ids: `officers, primers, helper, sq1, sq2, sq3, sq4`. These are seven separate groups, a refinement of the spec's single "officers & primers & helpers" row, so roles can be finer.
- `run` implies seeing and marking every group. `reports` implies seeing every group. Write implies read. Mark implies see.
- Duty defaults must equal today's access exactly. The existing rules suites (49 and 117 checks) must pass unchanged.
- The Owner short-circuits to everything. Only the Owner writes `roles/*` and `staff/*`.
- Nothing is pushed to `main` until the user says so.

## Review Focus

1. **A role is edited while a member is signed in.** That member's screen should reload into the new access. Test: change a role in demo while previewing as a member.
2. **A role is deleted.** Its members should lose only what that role gave. Test: in a rules emulator case, delete a role and check that a member's other role still works.
3. **A login has no roles yet** (just after the switch-over or on a new login). It should get only Everyone's access. Test: a unit case `combine([])` equals Everyone.
4. **A See-only user presses an edit control or opens a modal.** There should be no edit buttons or primary actions, and the database should refuse writes. Test: browser case for Orders See-only, and a rules case.
5. **A Squad Leader record with a null squad.** It should be able to mark nothing, with no rules error. Test: a rules case.
